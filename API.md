# Locket API

The screens and any agent use the same HTTP API. Authenticate with a Base native session (sign in through `/signin`; an agent is an invited operator the owner gave the `agent` role). Commands are same-origin JSON: send `Origin` equal to the installation's origin and `content-type: application/json`.

## Reads

- `GET /api/locket/state` — everything the signed-in person may see: `actor`, `operators`, `parties`, `customFields`, `customValues`, `agreements`, `routes` (required approvals per open agreement), `requirements`, `versions` (with `text` and `digest`), `artifacts` (metadata), `comments`, `templates`, `templateVersions`, `playbooks`, `deviations`, `approvals`, `approvalReminders` (settings, preferences (own; owner sees all), pending approvals with next reminder/escalation times, sent reminders without addresses), `deadlineReminders` (offsets, sent renewal/obligation reminders, escalations, alternates and digests without addresses, provider events), `packages`, `executions`, `terms`, `obligations`, `renewals`, `notices`, `proposals`, `imports` (owner), `access`, `audit`. Rows use database column names. Restricted agreements and their records are absent for people without access.
- `GET /api/locket/clause-library?q=TOPIC` — `{results:[{id,libraryVersionId,libraryVersionNumber,templateName,clauseKey,clauseTitle,variantId,variantLabel,text,notes,ruleKey,rule,playbookVersionId,playbookNumber,acceptanceCount}]}` for approved template/library clauses. Counts are per distinct accessible executed agreement whose current packaged version retains an explicit insertion; ordinary template choices and superseded wording never count.
- `GET /api/locket/search?q=TEXT` — permission-scoped metadata and all-version text search using the repository executor. Results retain `match` (first passage or null) and add `matches:[{versionId,version,start,end,quote,excerpt}]`, one literal case-insensitive hit per matching paragraph/version. Use `definition=JSON` or `viewId=ID` instead of `q` for the same typed filters as `/repository` (including current-version `has_deviations` yes/no and `deviations` clause keys). A passage opens `#agreement/ID/versions/NUMBER/START/END`, unfolding and highlighting the original offsets. No passage is fabricated for a metadata-only hit.
- `GET /api/locket/compare?from=VERSION_ID&to=VERSION_ID` — `{from,to,lines:[{op:"same"|"del"|"add",text}]}` for two versions of one agreement.
- `GET /api/locket/files/ARTIFACT_ID` — the exact stored bytes; header `x-locket-sha256`.
- `GET /api/locket/export` — owner only: `{format:"locket-archive/1",exportedAt,records:{table:[rows]},files:[{...metadata,base64}]}`.

- `GET /api/locket/audit?person=OPERATOR_ID&agreement=AGREEMENT_ID&action=ACTION&from=YYYY-MM-DD&to=YYYY-MM-DD&q=TEXT` — owner/counsel only: `{rows:[audit entries]}`. All supplied filters intersect; UTC start/end dates are inclusive. Add `format=csv` to download the same rows. CSV records an `audit.export` event after selecting its rows; filtering and reading do not add entries. Restricted workspace/search/comparison reads record `agreement.view`; successful artifact downloads record `file.download`.

- `GET /api/locket/portfolio` — permission-scoped portfolio tiles (agreement ids, count, recorded USD cents, missing-value count), lifecycle projections and current-term notice countdowns. The same `portfolio` is included in workspace state.

## Commands

`POST /api/locket/commands` with `{commandId, type, payload}`. `commandId` is a UUID; retrying the same id and payload returns the first result, a different payload is refused (`IDEMPOTENCY`). Success: `{ok:true,result}`. Failure: `{ok:false,error:{code,message,details}}` with 400, 401, 403, 404, 409, 413 or 415. `STALE` means the record changed since it was read; reload and review. Commands that change an agreement after review take its current `version` (the agreement row's `version`). Files are `{filename, mediaType?, base64}` (5 MB each). Dates are `YYYY-MM-DD`; money is a decimal string in USD (`"48000.50"`).

## Published terms and clickwrap (`SIGN-004`)

Owner/counsel use `clickwrap.publish` with `{name,kind:"tos"|"dpa"|"partner",siteOrigin,body}` for version 1, then `{termsId,version,body,requireReacceptance:true|false}`. `version` is the terms record's current revision from state. Publishing trims outer whitespace and appends immutable UTF-8 text and its SHA-256; it never rewrites an earlier version. A required version prompts every account again; an optional revision preserves acceptance of the most recent required version.

The hosted review is `GET /api/locket/clickwrap/terms/TERMS_ID`. It refuses framing, displays the exact text, version, digest and identity, and requires an unchecked checkbox followed by **Accept**. A Base current-session user accepts as that account and email; agent-role accounts are refused. A missing Base session returns through sign-in; an invalid external assertion is never replaced with Base authentication. The same request through the API is `POST /api/locket/clickwrap/accept` with `{commandId,termsId,versionId,digest,accepted:true}`. Origin must be this installation and content type JSON. `POST /api/locket/clickwrap/show` `{termsId}` returns `{terms,identity,required}`. A changed current version is refused; reload and review before accepting.

For the customer's own website users, configure the optional server-only `CLICKWRAP_SIGNING_KEY` secret (32 or more characters) through private setup answers or the declared deployment secret. Share it only with the website's server; never ship it to its browser, log it or place it in a URL. No Locket account is needed for these users. The website server reads `GET /api/locket/clickwrap/published/TERMS_ID` and signs the following JSON as `base64url(UTF8(JSON)).base64url(HMAC-SHA256(key, firstSegment))`:

```json
{
  "installationOrigin": "https://contracts.example.com",
  "siteOrigin": "https://customer.example.com",
  "termsId": "published-terms-id",
  "versionId": "exact-published-version-id",
  "digest": "exact-published-sha256",
  "signerId": "website-account-id",
  "email": "person@example.com",
  "nonce": "fresh-random-value-at-least-16-characters",
  "issuedAt": 1792396800000,
  "expiresAt": 1792397100000
}
```

Times are Unix milliseconds, with a maximum ten-minute lifetime and no future issuance. `siteOrigin` must exactly match the terms' configured HTTPS origin (localhost may use HTTP). The site's server must derive signer ID and email from its authenticated user. Each nonce is consumed atomically once. Retrying the same command UUID and payload returns its first outcome without another acceptance; a new command cannot reuse that nonce. Site actor identities encode the site origin and signer ID as an unambiguous pair. Tokens pin installation origin, site, terms and version, so a new version requires a fresh assertion. These identities are recorded and shown as **site-asserted identity (not identity-proofed)**. The key never grants authoring, linking, search or export access.

Load `<script src="https://contracts.example.com/api/locket/clickwrap/embed.js"></script>` on the website, then call `LocketClickwrap.mount(element,{termsId,identity:signedAssertionFromYourServer})`. This adds a review link opening the hosted page in its own window. The assertion travels in a URL fragment, is removed from the address immediately, and is sent only in `Authorization: Bearer ASSERTION` on same-origin JSON show/accept calls. It is never a query parameter. The embed never accepts silently or in a frame. To use the HTTP API instead, send that Authorization header on show and accept with the same explicit consent fields and installation Origin. External requests use no Base cookies.

Every acceptance keeps account, email, identity kind, exact version/digest, server time, transport IP (empty when the transport supplies none), user agent, hosted page shown, and originating site. Caller-supplied evidence fields cannot override them. `GET /api/locket/clickwrap/acceptances?q=TEXT&terms=TERMS_ID&party=PARTY_ID` searches them; add `format=csv` to export matching evidence. Owner/counsel see all; other Base users see only their own Base-session acceptances. External assertions grant no acceptance-record reads. Owner/counsel link an acceptance to an existing visible counterparty through `clickwrap.link` `{acceptanceId,currentPartyId:null|PARTY_ID,partyId}`. Linking is audited separately from immutable acceptance evidence. Publishing, accepting, linking and exporting are audited. The complete owner archive includes all three clickwrap tables; `rer export`/`import` also includes the product tables through its existing portability policy.

For local configuration, keep the owner-only answers JSON inside the checkout (for example `.rer/local/clickwrap-answers.json`, mode 0600), with `CLICKWRAP_SIGNING_KEY` set to a server-only random key. Run `rer setup --answers .rer/local/clickwrap-answers.json --non-interactive`; this explicitly updates that optional setting while preserving existing owner and other private settings. Omit the field to preserve it; an explicit empty value disables the external door. Hosted operators provide the declared optional secret through the deployment environment or private environment file. The key is never included in product archives or rendered pages.

## Bulk renewal schedules (`RENEW-004`)

Owner/approver starts a whole-selection operation with `renewal.bulk.start` and `{agreementIds, ownerId, offsets}`. Repeated sequential `renewal.bulk.next` `{operationId}` requests preview the next internal batch; the final status is `reviewed`. The UI performs that sequence as one action and shows progress. State exposes only the actor's currently visible `reminderOperations`, so a reload can resume the same operation. After review, sequential `renewal.bulk.next` `{operationId, apply:true}` requests apply batches until `done`; a refused batch leaves earlier completed batches recorded, with resumable progress. There is no user-facing selection count cap; each internal batch holds at most 100 agreements.

The internal batch door `renewal.bulk.preview` accepts `{agreementIds, ownerId, offsets:[90,60,30,7]}`. IDs must be imported agreements visible to the actor; the active reminder owner must also be able to read every selected agreement. The result is a durable 30-minute preview with `tracked` current-term deadlines and `skipped` reasons (including missing confirmed terms, expired and terminated agreements). Offset instants are 09:00 in each agreement's zone. Past offset times are retained and labeled; they are never represented as delivered reminders.

After reviewing it, `renewal.bulk.apply` `{previewId}` applies exactly that actor's preview. Changed agreements/deadlines, lost access, an inactive owner or an expired/applied preview refuse the operation. Each guarded batch stores the selected owners and offsets, bumps tracked agreement revisions and audits every tracked/skipped outcome. `/api/locket/state` returns the person's visible `reminderSchedules`; later agreement or lifecycle changes mark a stored schedule `needs_review`. Applying sends no email (`deliveryStatus: "not_delivered"`); RENEW-002 then reminds the schedule's owner at its offsets while the schedule matches the current deadline, and its `deadlineReminders` messages and events are the delivery record.

## Approved notice delivery — RENEW-006

`notice.prepare` freezes a PDF letter and its recipient before `notice.approve`; state exposes `noticeLetters` with the artifact identity and SHA-256. An existing draft without a letter uses `notice.letter` `{noticeId}` first. Download it through the ordinary authenticated `/api/locket/files/{artifactId}` door. An existing approval without a frozen letter cannot be emailed: prepare and approve a new notice.

`notice.email` `{noticeId}` queues a one-use send to the approved recipient with the approved PDF attached. The installation must use Resend with its existing `MAIL_API_KEY`/`MAIL_FROM` and optional `NOTICE_RESEND_WEBHOOK_SECRET` configured through setup/deploy. The immutable command result is queued; `noticeDispatches` carries accepted/suppressed/rejected/rate_limited/uncertain/sending outcomes separately. No automatic retry follows an interrupted or uncertain call. Local/demo mail is suppressed and the notice stays approved, not sent.

Subscribe the Resend endpoint `/api/locket/notice-events/resend` to `email.delivered`, `email.bounced`, `email.delivery_delayed`, `email.failed` and `email.complained`; it records events for notices and for RENEW-002 deadline reminders (a first bounce of a reminder is retried once to an alternate recipient). This public POST door requires the real `svix-id`, `svix-timestamp` and `svix-signature` headers and validates the unmodified request body. It takes no session or browser Origin; signature timestamps have a five-minute tolerance. Events must match the stored message ID and exact recipient. `noticeEvents` retains history; provider reports never determine legally effective service.

The manual `notice.sent` payload accepts `trackingNumber` for `post` or `courier`. `notice.tracking` `{noticeId,trackingNumber,status:"unconfirmed"|"delivered",deliveredAt?,detail}` records subsequent manual evidence; delivered requires an ISO instant after sending, no later than now, and a note. Existing delivered evidence is immutable. `noticeTracking` and the event history distinguish these human records from signed provider events. State, downloads and complete archives use existing access and audit rules.

## Saved repository views — REPO-007

`view.save` `{name,definition,sharedRoles}` creates a private or role-shared definition. Include `{id,version}` to update your own current revision. `view.delete` `{id,version}` deletes your own definition; `view.pin` `{viewId,pinned}` changes only your own pin. Every human role may manage these preferences; agents are read-only. State returns only readable `savedViews`, parsed definitions/audiences, current revisions and the caller's personal pin.

A definition is `{query,filters:[{field,operator,value}],sort:{field,direction},columns:[field,...]}`. Field identities and kinds are the shared catalogue in `src/locket/repository-fields.ts`. Operators are `eq`, `contains` (text only), `gte`, `lte`; all filters match, bounds are inclusive, text comparisons ignore case, and USD decimal inputs compare as exact cents. Date values are ISO calendar dates; creation and update dates are UTC. The `department` text field uses the current department name: explicit owner classification takes precedence over the pinned intake department answer. Unclassified agreements have null. Agreement visibility is applied before department query, filters, sorting, projection and CSV; a department label grants no access. Current term and notice fields use the existing confirmed-term projection, never a proposed value. Sort uses identity to break ties and puts missing values last in either direction.

`GET /api/locket/repository?viewId=ID` executes a readable definition against the caller's currently visible agreements. Alternatively supply `definition=` with its JSON encoded as a query parameter for an unsaved preview. Results contain the definition, selected ordered column metadata, rows with only those column values and `evaluatedAt`; money values are integer cents. Add `format=csv` for the same executor's rows and order, formatted USD, quoted cells and formula-safe text. Sharing a definition never grants agreement access; private preferences remain hidden except in the complete owner archive. REPO-005 and REPO-009 inherit custom fields, real group audiences and field restrictions before those capabilities ship.

## Custom and scheduled reports — REPORT-002

`report.create` `{name,viewId,groupField,frequency:"weekly"|"monthly",format:"csv"|"pdf",firstAt:"YYYY-MM-DDTHH:mm",recipients:[operatorId,...]}` snapshots a readable saved view. `firstAt` is a future local minute in the installation's time zone, captured on the schedule. Each human can create personal schedules and stop their current revision using `report.stop` `{id,version}`; agents cannot write.

`GET /api/locket/reports/ID` returns the creator's freshly scoped groups and rows; `?format=csv` or `?format=pdf` downloads the same report. Dates group by calendar month; totals are integer USD cents, with missing amounts counted separately. Workspace state returns only the caller's `reports` and `reportDeliveries`. The hourly scheduler generates each recipient's attachment with their current access, preserving the captured local time across DST and clamping month-end. A provider-accepted status does not confirm mailbox delivery. Local/demo sends are suppressed; interrupted attempts are visible and never automatically resent.

## Personal notifications — NOTIFY-001

Workspace state includes `notifications.preferences` (`inApp`, `email`, `digest`, `timezone`) and the signed-in person's currently accessible `items` with generic kind, authenticated agreement link, read time and honest email outcome. No other person's inbox, delivery address or preferences appears here. Agent reads return an empty inbox.

`notification.preferences` sets those four fields for the current human only, preserving existing reminder delegates/alternates. `notification.read` `{id}` marks an accessible own item read. `comment.add` accepts `mentionIds:[operatorId,...]`: active humans with current agreement access, checked again in the command batch. Text such as `@counsel` alone never selects a recipient.

Request/responsible-person and confirmed-obligation assignments, pending commercial/exception approvals, explicit mentions and manual signature handoff/void/execution create new events in their business batch. Existing explicit approval emails, approval reminders and deadline reminders consult the same channel/digest choices. The hourly scheduler claims one own-zone daily digest at the first tick at or after 09:00; items arriving after that claim wait for the next local day. All pending source state, current authority/access and preferences are checked again in the claim. Replays, concurrent schedulers and uncertain provider outcomes cannot automatically send the same item again. Provider acceptance remains distinct from mailbox delivery; local/demo sends are suppressed. Deadline digests retain their original signed provider-event and alternate-bounce evidence through a real digest parent.

### AGENT-003 prepared notices

`notice.source {agreementId, quote}` lets a human select an exact executed text passage against the confirmed decision/deadline and recorded counterparty email/notice address. `notice.agent.prepare {sourceId}` prepares the labelled frozen PDF; agents may prepare but never select or approve. `notice.schedule {noticeId, pdfDigest, recipient, method, sendLocal}` approves the exact draft and a future local `YYYY-MM-DDTHH:mm` in the agreement zone with more than one hour of lead. ## Chat intake and status notifications

`POST /api/locket/chat-intake/slack` accepts Slack form-encoded `/contract` commands and `message_action` shortcuts with callback identity `locket_contract`. Configure the optional installation secret `CHAT_SLACK_SIGNING_SECRET`. The endpoint checks the raw-body HMAC and a five-minute timestamp window. It returns an ephemeral native form link for a command; a shortcut makes one private reply to the signed callback's HTTPS Slack actions address. Replays do not repeat the reply. No message content is imported. A ten-minute launch is bound to the exact current owner-mapped operator and mapping revision, creates no session, and is consumed atomically by `request.create` with optional `chatLaunch`. Current role, published form audience, typed answers and frozen routing still apply. A forwarded, expired, remapped or previously consumed launch cannot create another request. Ephemeral launches are omitted from the ordinary domain archive.

`notification.chat.identity` is owner-only and takes `{channel, providerId, operatorId, version}`. It records an exact Slack or Teams member mapping, never a grant of agreement access. `notification.chat.preferences` is self-only and takes `{channels, version}`; channels are `slack`, `teams` and `nook`, and default to none. Destinations use the existing `approval.channel.bind` owner command. These choices are separate from approval-channel consent.

Status delivery currently covers existing assignment, mention, approval and signature notification events. It reads current Slack conversation members or Teams chat members, requires a complete bounded result and a mapped active full-field reader for every human member, and requires the recipient to be present. Slack uses `conversations.members` and `auth.test` to identify only the connected bot service identity. Teams uses Microsoft Graph chat membership. Missing scopes, unknown members, pagination or access changes withhold the message. Restricted approval-channel actions use the same audience gate. Membership may change at the provider after it is checked; links always require current Locket authentication and access.

The atomic send claim repeats current mapping revisions, agreement access, source state, personal consent and destination revision. Generic messages contain an authenticated record link and no title, figure or comment text. Provider acceptance does not confirm delivery. Uncertain or interrupted sends are never automatically resent. The personal `chatNotifications` state includes consent and scoped receipts; only the owner sees identity mappings. Domain archives retain mappings, consent and delivery outcomes, without provider credentials.

Teams intake, Nook intake and status delivery, watcher subscriptions, complete lifecycle coverage and chat digest batching remain unfinished. Nook's compatibility API is currently missing. Daily-digest choices suppress chat sends with `chat_digest_not_available`; the existing email digest remains unchanged. Local and demo status messages are suppressed. The conservative identity and audience policy is pending ct approval.

## Workforce SAML and SCIM

Workforce provisioning starts disabled. The deployment supplies optional server-only `WORKFORCE_SCIM_TOKEN` (at least 32 characters), `WORKFORCE_SAML_ISSUER`, `WORKFORCE_SAML_SSO_URL` (HTTPS) and `WORKFORCE_SAML_CERT` (the pinned IdP signing certificate or public key). These bindings and the SCIM token are never returned in state or owner archives. No provider account is seeded or connected automatically.

A signed-in installation owner explicitly calls `workforce.configure` with `{version:0,enabled:true,consent:true,groups:[{id:"Counsel",name:"Counsel",role:"counsel",kind:"department"}]}`. Approved roles are counsel, approver, requester and viewer; each group creates its own managed group or department. Mappings are immutable after approval. Later enablement changes omit `groups` and supply the current revision. Disabling deactivates managed people, removes managed memberships and revokes their sessions. Re-enabling does not reactivate them. The owner separately enables identity-provider sign-in through the existing Settings identity door. Native Auth OIDC remains available.

The sign-in page offers **Continue with workforce SSO** when configured and approved. Register the installation's `/auth/saml/metadata` entity, `/auth/saml/callback` POST recipient and persistent NameID at the IdP. `/auth/saml/start` creates a five-minute, browser-bound, one-use request. Both response and assertion signatures are required, together with exact issuer, audience, destination and recipient. Unsolicited, replayed, expired, weakly signed, redirected and unprovisioned identities are refused. Only the provisioned external subject chooses the account; incoming email attributes never choose or replace an existing account. The SAML callback issues a normal native session after verification.

SCIM uses `/api/locket/scim/v2/Users` and `/api/locket/scim/v2/Groups` with the server-held bearer credential and SCIM JSON. It supports collection reads with equality filters and pagination, user creation, individual reads, full user replacement, and PATCH of `active` or `displayName`. User creation requires an immutable `externalId`, an email `userName`, display name and explicit active flag. Existing local accounts and owners cannot be adopted. Stable subject and email changes are refused. Use the returned resource revision with `If-Match` for guarded updates. DELETE is refused; use explicit deactivation.

Groups are created only by the owner's mapping approval, then discovered through SCIM. PUT replaces members; PATCH adds, removes or replaces `members`, including the standard member-value removal selector. Only active managed people may join. Membership changes immediately update native intake membership and Locket roles and revoke old sessions and outstanding email links. Different mapped roles on the same person fall back to viewer. Direct manual role or managed-audience edits are refused. Every provisioning change rechecks the consenting owner's current active identity and configuration revision in the same atomic batch and records an attributed audit.
